Backend API routes to implement:

1. Worker registration/status route

GET /api/worker/status/

Purpose:
Return current authenticated worker status.

Response example:
{
  "worker_id": "caden-desktop-1",
  "status": "idle",
  "last_seen_at": "...",
  "current_job_id": null
}

2. Heartbeat route

POST /api/worker/heartbeat/

Request example:
{
  "worker_id": "caden-desktop-1",
  "worker_name": "Caden Desktop",
  "status": "idle",
  "current_job_id": null,
  "stage": "idle",
  "progress": 0
}

When processing:
{
  "worker_id": "caden-desktop-1",
  "worker_name": "Caden Desktop",
  "status": "processing",
  "current_job_id": 123,
  "stage": "analyzing",
  "progress": 42
}

Backend behavior:
- Update worker last_seen_at.
- If current_job_id is provided, update that video's worker_last_seen_at, analysis_stage, and analysis_progress.
- Do not mark a job complete from heartbeat alone.
- If heartbeat stops for more than a configurable timeout, the backend should be able to treat the worker as offline/stale.

3. Get next pending job

GET /api/worker/jobs/next/

Purpose:
Return the next available pending analysis job.

Important:
This route should not permanently assign the job unless the design intentionally combines fetch+claim. Prefer separate fetch and claim.

Response if available:
{
  "job_id": 123,
  "video_id": 123,
  "title": "Sample Clip",
  "description": "...",
  "video_url": "https://...",
  "created_at": "...",
  "analysis_status": "pending"
}

Response if none:
{
  "job": null,
  "message": "No pending jobs"
}

4. Claim job

POST /api/worker/jobs/{job_id}/claim/

Request:
{
  "worker_id": "caden-desktop-1",
  "worker_name": "Caden Desktop"
}

Backend behavior:
- Atomically claim the job only if its current status is "pending", "failed retryable", or stale "processing".
- Set analysis_status = "processing".
- Set analysis_stage = "claimed".
- Set analysis_progress = 0.
- Set worker_id.
- Set worker_name.
- Set worker_claimed_at.
- Set worker_last_seen_at.
- Set analysis_started_at.
- Return success if claimed.
- Return conflict if already claimed by another active worker.

Response success:
{
  "success": true,
  "job_id": 123,
  "analysis_status": "processing"
}

Response conflict:
{
  "success": false,
  "error": "Job already claimed"
}

5. Update job progress

POST /api/worker/jobs/{job_id}/progress/

Request:
{
  "worker_id": "caden-desktop-1",
  "stage": "downloading",
  "progress": 15
}

Backend behavior:
- Only allow the worker that claimed the job to update it.
- Update stage, progress, worker_last_seen_at.
- Reject if job is not assigned to this worker.
- Reject if job is complete/cancelled.

6. Complete job

POST /api/worker/jobs/{job_id}/complete/

Request example with placeholder analysis:
{
  "worker_id": "caden-desktop-1",
  "summary": "Placeholder analysis summary for this dashcam clip.",
  "tags": ["dashcam", "driving", "placeholder"],
  "events": [
    {
      "timestamp_seconds": 3.5,
      "label": "placeholder_event",
      "description": "Fake event generated by placeholder analyzer",
      "confidence": 0.5
    }
  ],
  "metadata": {
    "analyzer_version": "placeholder-0.1",
    "processed_by": "caden-desktop-1"
  }
}

Backend behavior:
- Only allow completion by the worker that claimed the job.
- Save the placeholder analysis data.
- Set analysis_status = "complete".
- Set analysis_stage = "complete".
- Set analysis_progress = 100.
- Set analysis_completed_at.
- Clear or preserve worker_id depending on preferred audit behavior. Prefer preserving worker_id for audit.
- Return updated video/job data.

7. Fail job

POST /api/worker/jobs/{job_id}/fail/

Request:
{
  "worker_id": "caden-desktop-1",
  "error": "Download failed: timeout",
  "stage": "downloading"
}

Backend behavior:
- Only allow the claiming worker to fail the job.
- Set analysis_status = "failed".
- Set analysis_stage = "failed".
- Save error.
- Set analysis_failed_at.
- Set progress to current or 0.
- Job can later be retried manually or automatically.

8. Cancel/release job

POST /api/worker/jobs/{job_id}/cancel/

Request:
{
  "worker_id": "caden-desktop-1",
  "reason": "Worker stopped by user"
}

Backend behavior:
- Only allow the claiming worker or admin to cancel.
- Set analysis_status = "cancelled" or return it to "pending" depending on desired behavior.
- For MVP, prefer returning to "pending" if the user manually stops the worker before analysis finishes.
- Save cancellation reason in metadata/error field.
- Clear active processing state if needed.

Recommended behavior:
If the desktop worker is intentionally stopped, release the job back to pending unless partial processing results matter.

9. Admin retry route

POST /api/admin/jobs/{job_id}/retry/

Purpose:
Allow an admin to retry failed/cancelled jobs.

Backend behavior:
- Set analysis_status = "pending".
- Clear analysis_error.
- Reset progress/stage.
- Keep historical timestamps if useful, or overwrite depending on current model style.
